# Conference implementation status

11 October 2026. Guest-list foundation, QR/email/RSVP, online gate, attendance reporting, browser badge printing and walk-in registration with pre-entry QR tags implemented. Not deployed to production; module enabled in local development.

## Completed behavior

- Administrators can create dedicated guest-desk-only accounts and assign registration, gate, reporting or manager duties atomically. The dedicated role has no institutional permissions, is excluded from the member portal, and only exposes assigned events. The proxy and live server authorization restrict private pages/APIs; staff sign in directly to the guest desk and have their own password/sign-out controls. See `docs/CONFERENCE_STAFF_ACCOUNTS.md`.

- The conference UI now uses a task menu under **Conference guest desk**, separate registration/search/upload/settings screens, direct guest-card tag printing, guided gate and printing steps, plain-language status labels and responsive controls. Advanced invitation and team actions are collapsed. See `docs/CONFERENCE_STAFF_GUIDE.md` for the current button names.
- UI verification passed: production build, typecheck/lint and existing isolated API/SMTP/browser suite, including task-menu navigation, separate settings, phone registration/search, reopening a tag from its guest card, QR camera check-in, printing confirmation and attendance layout. Checks used synthetic guests; no real guest emails or physical tags were sent/printed.

- Reuses the event CMS, member registrations, institutional accounts, console styling and audit table.
- Adds event settings, guest identities, per-event staff assignments and private import previews.
- Provides `/admin/events/operations` with event selection, name/email search, pagination, VIP/VVIP and other categories, CSV template/preview/commit and manual staff entry.
- Import commits are transactional, retry-safe by batch ID, and serialized per event. Capacity includes existing active member registrations. All preview errors must be corrected before commit; there is no silent partial import.
- Super/Secretariat administrators have global module access; other active institutional staff require event assignments. Manager can manage settings/guests; RegistrationOfficer can manage guests; ReportingOfficer can read. Only institutional administrators can grant/revoke assignments.
- Browser mutations require the configured `NEXTAUTH_URL` origin and are rate limited. Guest data does not use preview fallbacks or public storage.
- Critical guest/config/import/staff audit entries share the mutation transaction; audit failure rolls back the operation.
- Existing member registration API response remains compatible. When the module is enabled, configured invitation-only events reject self-registration on the backend and show Invitation only in the portal. Other events preserve registration behavior.
- Committed previews remove their guest payload immediately. Uncommitted previews expire after 24 hours; new uploads opportunistically purge expired payloads for that event. A daily purge command covers inactivity.
- Selected guests receive independently generated, opaque QR/RSVP credentials. Recoverable credentials use AES-256-GCM with a dedicated runtime key; lookup tokens are hashed. No personal details are encoded in QR content.
- Staff can issue/queue, resend, regenerate or revoke invitations. Dispatch request keys are idempotent; credential creation, jobs, result and staff audit share one transaction. Resend retains credentials; regeneration invalidates old QR/link/session versions.
- Real SMTP support targets the user's existing cPanel/domain mailbox. A durable MySQL worker produces a branded email with inline QR, downloadable PNG and Unicode-capable PDF. Delivery state distinguishes queue/sending, SMTP acceptance, failure, uncertainty and cancellation.
- `/invite` exchanges a URL-fragment capability for an encrypted HttpOnly guest session, removes the token from the address bar and offers simple accept/decline plus QR/PDF downloads without an account. Pending RSVP does not withhold QR. Decline does not cancel registration; repeat identical responses do not duplicate history.
- Guest pages and APIs use no-store/noindex/no-referrer, same-origin mutations, rate limiting and the existing nonce CSP. Guest/session/credential expiry and revocation are checked on every read/write.
- The Node 22 worker is bundled beside standalone `server.js` by the production build; its runtime, font and SMTP pipeline were tested from the standalone directory against a local capture server.
- Event-scoped gate staff can verify entry QR codes by camera or reader, review the guest and record first admission. Concurrent/repeated confirmations cannot create a second admission; invitation regeneration preserves admission history. Manual lookup/admission records an identity-check reason and enforces the same invitation rules.
- Accepted RSVP is optional at the gate and disabled by default; managers can explicitly require it. Disabled events, cancelled registrations and expired/revoked/missing invitations block entry. Admitted guests have a 100 × 140 mm Unicode badge PDF; download audit does not claim physical printing.
- Event-scoped reporting includes active versus historical attendance, RSVP/category counts, print-state counts, a paginated directory and audited CSV export. Summary reads are consistent snapshots; exports neutralize spreadsheet formulas and omit credentials/manual reasons.
- Browser printing uses durable, idempotent requests and immutable 100 × 140 mm badge snapshots. Authorized operators/managers explicitly confirm physical collection or cancel; dialog events never mark a badge printed. Reprints require a reason and transition history is append-only. Physical hardware/driver validation remains outstanding.
- Staff can register walk-ins without email or guest accounts and prepare a QR tag before admission. Walk-in registration is idempotent, capacity checked and audited; RSVP is recorded as accepted. Tags use the same entry credential as invitation emails. Registration and printing do not increment gate attendance. See `docs/CONFERENCE_WALKIN_SETUP.md` for desk and dignitary workflows.

## Migration and changed areas

`prisma/migrations/20261011100000_conference_foundation/migration.sql` adds four conference tables; extends event registrations with nullable attendee linkage, category and invitation source; makes user linkage nullable for account-free guests. Existing IDs, user/event uniqueness, status and records are retained. No live attendee backfill is needed for this phase; the directory reads legacy member identities through User.

`prisma/migrations/20261011120000_conference_invitations/migration.sql` adds invitations, idempotent dispatch records, durable email jobs, email attempts and guest RSVP history; adds the separate Pending/Accepted/Declined RSVP field on existing registrations.

`prisma/migrations/20261011140000_conference_gate/migration.sql` adds the unique first-admission record and restricted registration/actor foreign keys.

`prisma/migrations/20261011160000_conference_printing/migration.sql` adds print requests, immutable rendering snapshots and transition history. Apply all four migrations before activating this application version, including when the feature flag is off. Reapply appropriate database grants after migration; hardening omits UPDATE/DELETE on guest RSVP, admission and print-transition history.

Source areas: `prisma/schema.prisma`, `lib/conference/`, `app/api/v1/conference/`, `app/admin/events/operations/`, `components/conference-guest-tools.tsx`, existing console navigation and portal event routes/component, `.env.example`, README and package scripts. Test/purge scripts live in `scripts/`.

APIs under `/api/v1/conference/events/:eventId`:

- `GET/PATCH /config`.
- `GET/POST /guests`.
- `POST /imports` creates a private preview, including validation errors.
- `POST /imports/:batchId/commit` commits only the requesting operator's valid unexpired preview; repeats return its original result.
- `GET/POST /staff` reads assignments or assigns/revokes existing staff by email.
- `GET/POST /invitations` reads delivery/readiness metadata or performs bulk lifecycle operations with a UUID Idempotency-Key, up to 100 registrations/request.
- `GET/POST /gate` looks up guests, verifies entry QR or records duplicate-safe first admission; `POST /gate/badge` produces an audited printable PDF after admission.
- `GET/POST /reports` reads attendance and exports private audited CSV; `GET/POST /prints` reads/prepares/finalizes authorized badge print requests. See [CONFERENCE_REPORTING_PRINTING.md](CONFERENCE_REPORTING_PRINTING.md).

Guest APIs under `/api/v1/conference/guest`: POST token-exchange, GET invitation, GET QR, GET PDF, POST RSVP. Source additions include credentials/invitation/rendering/worker/guest-session services, guest and staff delivery components, `/invite`, private route headers, an open-source bundled Noto font/license and standalone worker packaging. Configuration and operational details are in [CONFERENCE_EMAIL_SETUP.md](CONFERENCE_EMAIL_SETUP.md).

## Limits and next phase

QR/email/RSVP, online gate verification, duplicate-safe first admission, attendance reporting and browser/PDF badge printing workflows are implemented. SMTP settings and worker scheduling are not configured on a real host. No real guest emails or physical print jobs were sent. Printer-specific integration and a live host/device rehearsal remain outstanding. See [CONFERENCE_GATE_SETUP.md](CONFERENCE_GATE_SETUP.md) and [CONFERENCE_REPORTING_PRINTING.md](CONFERENCE_REPORTING_PRINTING.md).

CSV only, maximum 500 rows/512 KB per batch. The initial identity policy supports one attendee per email; shared email addresses are rejected for review. This is a deliberate initial restriction compared with the broader proposed shared-contact model. Existing attendee details are never overwritten by an import for another event. Organization/title are contact attributes in this phase rather than a separate employer directory. Guest edit/cancel, companions, operational lifecycle, Excel and advanced session/access features remain subsequent work.

The module flag and per-event setting both default off. During local console setup, the existing local database was backed up, all seven conference migrations were applied, and the module flag and credential key were configured privately in `.env.local`. Per-event operations still require activation from Conference operations. SMTP configuration and production deployment remain outstanding. No production archive was regenerated. Applying this phase to production requires a validated release package, additive migration, backup/restoration plan, persistent settings and scheduled preview purge. Apply the migrations before activating the new application version, even with the module flag off, because the generated Prisma client expects the extended registration schema. The existing `deploy/REPORT.md` describes the prior production package and is not a verification report for this change.

Conference operations is accessible from the desktop/mobile console navigation, the Operations overview card, and the Events page. When the module flag is off, its page explains the required setup instead of hiding the entry point.

Next phase: choose and rehearse the printer/workstation/stock, validate staging deployment/rollback and the end-to-end workflow on the real hosting environment and gate devices. Printer-specific silent integration and approved operational exceptions/re-entry remain future work. Existing cPanel SMTP is the chosen delivery service. Its exact hostname/mailbox credentials and a host-supported worker supervisor/schedule still need private runtime configuration.
